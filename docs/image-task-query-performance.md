# 异步生图状态查询与分段耗时

## 范围

覆盖融合、智能编辑、重新打光、裂变、精修和文生图共用的图片任务链路。本批实现状态查询独立预算、服务端读取时间提示，以及领取、查询、转存和结算的分段日志。

2026-10-15 正式站单次样本中，智能编辑完成发现约 8.527 秒，其中一次上游查询本身约 5.302 秒；融合模型生成约 35.778 秒。该数据用于确定排查方向，不是平均值或 p95。本批没有更换模型、移动部署区域或降低输入和输出分辨率。

## 状态查询预算

百炼千问图片任务使用两套预算：

| 操作 | 配置 | 默认 |
|---|---|---|
| 生成提交、结果下载 | `QWEN_IMAGE_REQUEST_TIMEOUT_MS` | 30 秒 |
| 单轮状态查询总预算 | `QWEN_IMAGE_STATUS_TIMEOUT_MS` | 8 秒，范围 1–30 秒 |
| 单轮状态查询内部重试次数 | `QWEN_IMAGE_STATUS_RETRY_COUNT` | 0，最多 1 次 |

状态查询预算覆盖等待响应头、读取和解析正文，以及可选重试的等待。正文读取超时必须产生可恢复的查询错误，不能被 JSON 解析回退吞掉后误记成成功的 `UNKNOWN`。

`QWEN_IMAGE_REQUEST_RETRY_COUNT` 不再控制状态查询。生成 POST 仍由已有持久化执行协议决定是否可以重发，不在适配器内自动重发。查询瞬时失败后保留原任务编号和预扣记录，下一轮只查询原任务；原截止、退款、迟到结果、租约令牌和幂等结算规则保持原行为。

## 前后端时间对齐

- 图片任务的活跃响应增加可选 `pollAfterMs`，根据当前服务端时间与已经保存的 `next_poll_at` 计算，限制在 1–30 秒。
- 传相对等待，避免浏览器与服务器时钟偏差。复用浏览器查询缓存的观察者会扣除快照已等待的时间。
- 工具页采用该提示；旧服务端缺少提示时沿用百炼 1 秒、其他图片 2 秒。视频仍为 5 秒，终态停止轮询。
- 服务端百炼上游查询仍至少间隔 3 秒，数据库租约仍是唯一推进权来源。本批没有通过更密的上游请求换取性能。
- 任务中心只从原有只读快照投影读取提示，按可见活跃任务的最近时间刷新，范围 1–8 秒。推进时间已经到期但后台尚未更新时保留 8 秒观察，避免无进展时持续空读。不可见任务、待确认回执及旧服务端也保留原有 8 秒观察；空闲 30 秒，错误仍按原退避。
- 任务中心不会调用生成、补提交或业务推进函数。工具页关闭后，服务端推进仍依赖已有维护执行器；刷新频率不能消除维护调度自身的等待。
- 投影仅增加现有 `next_poll_at` 列的读取，没有表结构、RLS、迁移或线上配置变更。

## 观测字段

`evt=image-job-phase` 的固定字段为任务和原请求编号、供应商、模型、运行环境、`phase`、`ms`、`outcome`，部分事件带序号和 `scheduledLateMs`。不读取或输出提示词、图片、签名 URL、对象键及异常正文；日志异常不能改变业务结果。

活跃图片响应另记录 `evt=image-job-poll-hint`，使用响应实际返回的 `pollAfterMs`，按任务、原请求和环境关联。浏览器在共享查询真正发出时记录 `evt=task-poll-request`；多个观察者只产生一条请求日志，不在间隔函数每次重算时输出。

| 浏览器字段 | 含义 |
|---|---|
| `pollAfterMs` | 有效的服务端原始提示；无效或缺少时为 `null` |
| `intervalMs` | 最近有效调度计划选用的等待时间，已扣除快照缓存时间 |
| `cachedElapsedMs` | 选择该计划时，快照已经在缓存中等待多久 |
| `source` | `server` 采用提示；`fallback` 沿用旧间隔；`video` 视频固定间隔；`unscheduled` 没有可关联的活跃计划，例如首次查询 |
| `fallbackReason` | `missing_hint` 或 `invalid_hint`；未回退时为 `null` |
| `actualWaitMs` | 从计划建立到本次真实请求的时间 |
| `actualIntervalMs` | 同一共享查询两次实际请求开始的间隔；首次为 `null` |

每个观察者保留有效计划；同快照、同间隔的重算不会重设记录时间。多个观察者共存时关联最早到期的计划，退出或禁用时移除自己的计划。聚焦、手动刷新或浏览器后台节流都可能影响实际发起时间，因此计划字段不能单独证明是定时器触发，应结合 `actualWaitMs`、`actualIntervalMs` 与网络记录判读。浏览器日志仅在开发者控制台输出，没有新增遥测上传接口。

| `phase` | 范围 |
|---|---|
| `lookup` | 原任务查询事务，包含身份上下文、读取、到期收口及可能的领取 |
| `lease` | 领取执行权的数据库操作，是 `lookup` 的子段 |
| `prepare` | 推进前短事务与截止状态确认 |
| `reconcile` | 原提交回执和原结果对象的恢复读取 |
| `status` | 一次供应商完整状态查询，含该轮内部重试 |
| `download` | 供应商结果响应及完整正文读取 |
| `postprocess` | 尺寸校验与必要的裁切编码 |
| `transfer-intent` | 原结果转存意图短事务 |
| `store` | 结果写入对象存储 |
| `billing` | 原账本结算或释放调用 |
| `persist` | 持有有效令牌的推进写回事务，包含可能的 `billing` 子段；原名 `finalize`，不表示每次都结算 |
| `present` | 推进请求后的响应组装和结果签名；普通快照及重复终态读取不记录该段 |

`scheduledLateMs` 是开始查询时相对 `next_poll_at` 的迟到时间，包含调度、领取竞争与前置恢复等等待，不能归为模型生成时间。父子段不能重复相加，多图并行阶段也不能相加当成端到端耗时。

百炼原有 `qwen-image-status` HTTP 日志另增加 `responseHeadersMs`、`responseReadMs` 和本轮 `timeoutMs`。等待响应头包含连接、请求和上游等待，不能当作纯建连耗时；正文阶段包含 JSON 解析。

`billing` 只表示原账本的结算或释放调用；它和 `persist`、`present` 都不是额外的计费状态。普通终态读取仍按原接口返回结果并签名，可保留 `lookup` 请求耗时，不再重复制造展示或完成事件。已有按 `phase=finalize` 查询的日志筛选需改为 `persist`。

## 转存意图回执

`image_job_attempts.kind=transfer` 的 `outcome=accepted` 表示对象结果已经在有效租约下发布到原任务明细。正常上传后的结果发布，以及恢复时通过对象类型和 SHA-256 校验后的发布，都会在同一个数据库事务补齐该回执。最终事务回滚时，明细和回执一起回滚。

仅 PUT 返回成功不足以确认发布。上传中断、发布失败、租约失效、对象不存在或校验失败时保留待确认状态；清理中的意图、其他序号或其他对象不会被误确认为成功。`store` 阶段的 `outcome=success` 只说明 PUT 调用返回，两者含义不同。

复用现有尝试表权限、租约校验与账号及环境隔离，无新增迁移、账本状态或供应商提交。此次只补齐后续正常发布和恢复发布的回执，没有批量回填历史已完成记录。

## 验收

本地回归覆盖查询预算包含正文和退避、生成提交独立、超时后复用原任务号、预扣一次与结算一次、读取时间边界、多观察者去重、任务中心只读、账号与环境隔离。数据库投影通过本地 PGlite 的真实 SQL、只读事务和权限测试验证。

2026-10-16 全量测试为 268 个文件、1777 项通过，无未处理错误；构建、lint 和差异格式检查通过。Chrome 本地验收使用真实轮询组件、百炼查询适配器和内存任务执行器连接模拟供应商：首次状态查询故意超过 120 ms 模拟预算，第二轮读取同一个任务成功，生成提交、预扣和结算各一次。工具页在提交后约 15 ms 建立初始快照，后续读取约为 3546 ms 和 7049 ms，未在中间每秒重复读取。工具页和任务中心均显示成功。

该流程使用本地模拟图片、存储和计费接口，不代表真实百炼、线上账本或正式站提速验收。证据与截图保存在 `/tmp/pixel-image-query-20261016/`。
