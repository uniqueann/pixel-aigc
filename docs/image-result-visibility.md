# P2-B：结果发现到页面展示

## 目标与口径

沿用“服务商完成到页面可见约 4 秒”的目标。服务商生成耗时单列；完整工具耗时、服务器收到成功到响应就绪、浏览器收到响应到图片可见分别记录，不能用其中一段代替完整目标。

服务商有可靠完成时间时，用原任务的完成时间与浏览器图片加载并获得绘制机会的时间关联，明确时区和时钟偏差。没有可靠完成时间时，只报告可观测的局部分段，不从供应商的预估生成秒数反推出完成时间。报告保留逐条样本、样本量、失败、超时、缺失、p50/p95 和超过 4 秒的样本；小样本不代表长期稳定性。

## 改动

- 服务端以本轮最后一次 `getStatus` 操作的开始时间计算下一次查询时间。查询、收尾和返回已经消耗的时间会体现在较短的剩余 `pollAfterMs` 中，浏览器继续使用原提示协议。
- 多个上游任务号按最后一个查询起点计时，避免后面的任务被过早查询。首次提交后的等待保持原策略；未执行查询的推进沿用原行为。
- GPT Image 2 默认后续查询从 5 秒改为 3 秒，首次仍为 5 秒。显式配置较长间隔时保留配置；后续间隔仍不低于 3 秒。千问默认 3 秒、视频原策略均保留。
- 没有发现恢复补丁时，省去额外的空写回事务。恢复读取与校验、最终发布时的租约校验、结果转存回执和账本事务仍使用原流程。
- 前端仍复用同账号、同环境、同任务的共享查询；缓存等待扣减、最小等待、终态停止和账号切换取消保持原协议。图片校验和解码通过后才进入结果区，历史保存继续异步进行。

本批没有新增后台轮询循环，也没有自动重提已受理或失败的生成任务。一个推进请求仍只执行原有一轮状态读取；适配器内部的重试策略保持原配置。查询超时预算、平台限流退避、任务截止和结算幂等性不变。

## 成本与回退

缩短 GPT 查询间隔会增加长任务期间的状态查询、函数和数据库用量。健康链路下，GPT 的查询次数可能增加到原来的约 1.7–2 倍；千问主要消除查询耗时的叠加。复测必须同时记录查询次数、超时/限流和积分流水，不能只比较显示速度。

若状态接口或数据库负载明显恶化，可把 `DRAGONCODE_POLL_INTERVAL_MS` 配回 `5000` 或更长；较长配置会保留。业务区域继续使用 `pdx1`，模型、分辨率、输出字节与收费规则保持原配置。

## 验证

自动化覆盖：

- 1.2 秒查询后只再等待 1.8 秒，多个前端观察者仍只发送一次查询。
- 查询超过一个间隔时只返回剩余提示，不在同一个请求里连续追赶查询。
- 多任务号从最后一次查询计时，平台已持久化的较晚退避不被提前。
- 查询超时后读取原任务，原生成提交和预扣不重复；恢复发布、旧租约拒绝、失败退款及账号/环境隔离继续回归。

浏览器受控对照使用真实任务服务、轮询组件、工作站控制器、私有结果读取、解码和候选图组件。供应商、数据库延迟、对象存储及账本使用本地替身，并在页面显式标注。比较 `origin/main` 基线和本次实现，模拟相同生成、查询、结果下载和转存延迟；从模拟供应商完成测到图片加载后的绘制机会。该结果仅验证链路行为，不作为真实供应商或生产提速结论。

真实复测建议先使用同一模型和分辨率的小批样本，记录原任务号、供应商完成时间、状态查询、下载/转存、浏览器图片可见时间及账本。收费样本需先明确积分上限；失败样本不自动补跑。四秒目标只有取得对应完整证据后才能标为通过。
