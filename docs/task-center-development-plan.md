## 1. 要解决的问题与完成标准

用户在生成过程中切换工具、刷新页面或关闭浏览器后，应能重新找到已经提交的任务，看到可信的执行与积分状态，并进入对应工具查看结果。

本期完成标准：

1. 已提交的图片任务不再依赖某个工具页面持续轮询；浏览器关闭后，服务端仍能查询上游、保存结果并完成积分结算。
2. 侧栏能统一发现进行中任务和近期未查看的终态任务，刷新后可以重新读取。
3. 点击任务进入对应工具与任务；有未保存草稿、原画布不可打开等情况时，可以先查看只读详情与结果。
4. 打开任务、恢复等待、刷新列表都不会重新提交生成；收费重试必须由用户明确触发。
5. 任务状态、结果可用性、积分结算分别展示，不能用一个红绿灯替代三个不同的事实。

任务中心负责执行过程和结果入口；“我的资产”继续负责素材管理，“积分明细”继续负责账本查询。

## 2. 当前基线与需要修正的认识

| 功能 | 当前恢复能力 | 本期要补的能力 |
| --- | --- | --- |
| 自由画布文生图、裂变 | 提交前持久化本地恢复记录；刷新后可继续查询并替换占位图；未取得任务编号时已有继续/放弃流程 | 纳入全局发现；补图片后台推进；按原项目、场景定位，复用既有恢复流程 |
| 工作站智能编辑、重新打光、融合、精修、裂变 | 页面内存持有当前任务；同步返回图片的模型会在提交请求内保存服务端结果，异步模型主要靠页面查询推进 | 后台推进异步任务；刷新后重新找到任务；恢复当前任务展示与结果 |
| 视频生成 | 已有分钟维护、回调、租约、结果转存与结算；结果可进入资产 | 复用现有后台，统一展示、定位、通知；补真实视频端到端验收 |
| 消除、重绘、扩图 | 同步请求将结果写入服务端临时存储；前端完成本地历史保存后可进入资产；请求途中刷新可从积分结果查询找回 | 将真实 `sync_credit_jobs` 记录纳入列表，直接查看已有结果，避免只能从积分明细绕行 |
| 抠图 | 在线请求；成功结果有本地历史及队列快照，刷新可恢复已保存的队列；进行中的请求不能自动接续 | 纳入在线任务发现，恢复服务端结果与本地已完成项；覆盖免费额度分支 |
| 转比例的智能扩展 | 使用在线扩图能力，可能产生积分消耗 | 每个已提交子任务接入统一列表；不承诺恢复整批尚未提交的图片队列 |
| 邮件助手 | 已有服务端任务、结果与超时维护；批处理有自身控制器 | 纳入已提交的服务端任务，定位单项结果；复用原批处理恢复逻辑 |
| 水印、普通转比例、当前本地批量流水线 | 主要使用浏览器内存，刷新可能丢失 | 本期保留原流程；本地队列持久化单独规划 |

当前图片任务查询会触发推进，而每日图片清理主要处理超时与清理；新增全局列表本身不能替代服务端后台维护。

2026-10-11 的生产只读检查确认：视频分钟调度处于启用状态，维护接口有完成日志；当时没有真实视频任务。这能证明调度链路在运行，不能证明真实视频生成、转存与扣费全链路已经验收。既有相关测试通过也只是现状基线，不代表本文新增功能已完成。

同步工具的临时对象按发布约定配置 7 天生命周期，正式上线前必须实查桶策略；相关七天迁移清理的是 `sync_requests` 耗时记录，`sync_credit_jobs` 当前没有同样的记录过期列。签名地址常用 15 分钟有效期，本地已保存字节独立管理，不能混为同一个“7 天”。详见[阶段 1 保留时间契约](task-center-contract.md#33-结果可用性与保留时间)。

## 3. 产品交互

### 3.1 全局侧栏

位置：导航菜单下方、账号区域上方。侧栏常驻最多 5 条，标题显示进行中数量，并提供“查看全部”。

排序规则：进行中优先；剩余位置展示近期未查看的失败、部分完成和完成任务。同组按时间倒序。完整历史在抽屉中查看。

每条显示工具名称、状态文字、完成数量、相对时间。例如“裂变 · 处理中 · 2/4”。完整参数、错误详情、积分明细和大图不挤入侧栏。

任务区有独立的高度上限与滚动；空间不足时减少可见行数。侧栏收起或窄屏时显示任务图标与进行中数量，点击打开同一抽屉。导航和账号操作始终可达。

### 3.2 统一状态表达

| 显示 | 含义 | 展示规则 |
| --- | --- | --- |
| 黄灯 + 排队中/处理中 | 服务端任务仍未结束 | 有真实进度才显示百分比，否则显示完成数量或等待状态 |
| 绿灯 + 已完成 | 任务生成成功 | 结果尚在转存时继续显示处理中，不能提前报完成 |
| 绿灯 + 部分完成 + 提示图标 | 部分结果可用 | 明确显示“2/4 已完成”、失败项与实际积分结算 |
| 红灯 + 失败/已超时 | 服务端确认失败或到达截止时间 | 另行显示已退回、等待结算等积分状态 |
| 灰灯 + 状态暂不可获取 | 网络断开、查询失败或提交结果尚待确认 | 保留上次可信状态，不能把客户端断网改成任务失败 |
| 灰色说明 + 结果已过期 | 历史任务成功，但服务端临时结果已失效 | 保留原成功与结算事实；有本地素材时仍可查看 |
| 灰灯 + 已取消 | 服务端确实存在取消终态 | 本期不提供通用取消按钮 |

颜色必须同时配文字和图标，满足 [WCAG 的颜色使用要求](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)。

### 3.3 共用任务抽屉

- 筛选：全部工具/本工具，进行中/已完成/失败，支持分页加载近期历史。
- 详情：工具、模型、时间、完成数量、错误说明、结果预览与积分状态。
- 操作：查看/下载/复制已有结果、查看积分记录；从详情进入原工具，显式载入原参数或已有结果。“准备重新生成”只准备参数，收费提交仍通过原工具生成按钮。
- “已查看”和“从近期列表移除”只改变展示状态，不取消任务、不删除结果、不触发退款。
- 页面初次加载时不连续弹出历史完成通知；本次会话观察到的终态变化统一通知一次。

每个工具页通过“本工具任务”入口打开带工具筛选的同一抽屉；进入具体原任务时增加独立结果区，继续复用原生成、预览、项目保存和修改稿流程。

### 3.4 点击任务

点击任务统一先打开只读详情。工具页的“本工具任务”入口只设置筛选，不改变工作站输入、蒙版、画布项目、邮件文本或未提交队列。

阶段 5 已实现详情后的工具定位：先保护未保存编辑，再通过原画布门禁验证项目权限；默认只恢复任务与结果，参数另行显式载入。缺少原项目或输入时保留只读结果，具体边界以 [阶段 5 报告](task-center-stage-five.md)为准。

## 5. 数据模型与接口契约

### 5.1 保留现有业务任务与账本作为事实来源

| 统一来源类型 | 原有数据 | 覆盖功能 |
| --- | --- | --- |
| `image_job` | `aigc.image_jobs`、`aigc.image_job_items` | 工作站/画布图片任务及现有视频任务 |
| `sync_credit` | `aigc.sync_credit_jobs` | 消除、重绘、扩图、抠图及复用这些接口的工具 |
| `email_task` | `aigc.email_tasks` | 邮件单项服务端任务 |

新增任务中心是查询投影与展示层，不再创建一张复制执行状态的总任务表，不建立第二套计费状态机。

统一摘要至少包含：

| 字段 | 用途 |
| --- | --- |
| `sourceKind`、`sourceId`、`taskKey` | 稳定标识；`taskKey` 使用 `sourceKind:sourceId` |
| `requestId` | 与原提交幂等键对应，合并本地待确认记录 |
| `tool`、`capability`、`modelProfileId` | 工具筛选与可读标题 |
| `state`、`completedCount`、`requestedCount`、`errorCode` | 统一执行展示，保留原来源状态 |
| `billingState`、`creditsReserved`、`creditsCharged`、`creditsReturned` | 根据服务端记录与现有账本生成；免费任务明确显示无需扣分 |
| `resultAvailability` | 区分等待结果、可用、已过期、不可用 |
| `origin` | 安全定位原工具、画布项目与场景 |
| `createdAt`、`updatedAt`、`completedAt`、`resultExpiresAt` | 时间、排序与有效期说明 |
| `outcomeVersion`、`seen`、`dismissed` | 终态版本与展示状态，支持迟到结果重新出现 |

摘要不包含完整提示词、邮件正文、原图、蒙版或签名下载地址。详情按需读取并签名，避免侧栏轮询不断重新签名与下载文件。

前端缓存必须按 `userId + runtimeScope + sourceKind + sourceId` 隔离；环境从服务端运行配置读取，不能由查询参数任意指定。

阶段 1 已冻结字段映射、空值和样例，增加 `taskExpiresAt` 以区分任务记录与结果对象期限；签名到期只在详情结果中使用 `urlExpiresAt`。部分成功保持原成功终态，由数量与 `partial` 表达；待确认提交属于本地凭据，不伪装成服务端任务。完整定义以[任务契约](task-center-contract.md)为准。

### 5.2 新增来源信息

在三种原任务表上增加可空的 `origin`，新提交与任务创建在同一事务写入，旧客户端不传时仍可使用。

来源字段限制为：入口枚举、工具标识；画布额外允许 `projectId`、`sceneId`、`projectSource: local/cloud`。字段有长度、结构与工具白名单校验，不接受任意跳转 URL，不把文件、正文或提示词复制进来源。

来源只影响导航，不影响价格和生成请求指纹；同一请求重入时保留首次有效来源，不因来源变化再次扣费。原生成参数变化仍按现有指纹冲突规则处理。

旧记录优先根据能力及已保存操作参数推导工具；无法确定的来源使用任务详情兜底。不能猜测旧任务属于哪个画布项目。

同步编辑任务目前未保存完整原图、蒙版和全部参数。本期恢复的是执行状态和结果；工具页提供“已有任务”展示模式，不能宣称完整还原编辑现场。用户可显式将结果作为新编辑输入。

### 5.3 最小展示状态表

新增 `aigc.task_ui_state`，只保存已查看和隐藏状态：

- 主键：`user_id + scope + source_kind + source_id`。
- 数据：`seen_version`、`seen_at`、`dismissed_version`、`dismissed_at`。
- 已查看/隐藏按终态版本生效；迟到结果使失败任务出现可用结果时，重新提示用户。
- 版本根据原任务执行终态及结果身份生成；签名地址更新、邮件正文编辑不会再次触发完成通知。
- 进行中任务不允许从近期列表隐藏；展示记录不会被执行器或计费逻辑读取。
- 展示记录保留最多 30 天；来源先过期或被清理时同步清理对应记录。此清理不改变原任务、素材和积分账本。

沿用 `aigc_api`、`withIdentity`、成员状态及用户/环境 RLS 规则。任务展示写入前校验原记录归属，其他产品数据不可读取。

### 5.4 独立任务中心 API

现有 `/api/tasks` 集合接口按能力分流，未指定能力时不能直接当作全工具列表。新建独立接口，保留原接口兼容性。

| 接口 | 行为 |
| --- | --- |
| `GET /api/task-center?view=sidebar` | 返回最多 5 条摘要、进行中数量、未查看数量及快照时间 |
| `GET /api/task-center?view=history&tool=...&state=...&cursor=...` | 按工具/状态分页读取近期历史；默认 20 条，上限 50 条 |
| `GET /api/task-center/by-request/:kind/:requestId` | 只读定位已经提交的原请求，处理尚未收到任务编号的情况 |
| `GET /api/task-center/:kind/:id` | 验证归属后返回任务详情、可用结果与最新签名地址 |
| `PATCH /api/task-center/:kind/:id/presentation` | 按客户端观察到的版本记录已查看或隐藏，仅修改展示信息 |

实现要求：

1. 集合使用三种来源的服务端投影查询，显式约束用户与环境；不要让客户端全量下载三个历史库后拼接。
2. 侧栏的优先级查询与历史分页分开。历史按 `created_at + source_kind + source_id` 稳定排序，游标绑定筛选条件与首次查询的时间上界；新任务通过刷新出现。
3. 默认展示最近 30 天内仍保留的记录；邮件与临时结果继续遵守更短的原有效期。抽屉写清“近期任务”，不承诺永久历史。
4. 任务中心 GET 只读执行状态，不调用上游生成、补提交、推进或超时退款。退款和执行推进由后台及原业务流程完成，避免打开列表触发业务副作用。
5. 复用并提取已有快照、结果签名与所有权校验逻辑，不直接调用带推进副作用的 `loadImageTask` 充当详情读取。
6. 详情过期与任务不存在使用明确错误码；不能把结果过期写成生成失败。接口使用私有缓存策略，结果签名不落日志。
7. 查询先使用应用角色执行原表 SQL。若以后使用视图，必须验证 `security_invoker` 与目标 PostgreSQL 版本，避免视图绕过 RLS。

RLS 与视图行为依据 [Supabase RLS 文档](https://supabase.com/docs/guides/database/postgres/row-level-security)及[视图文档](https://supabase.com/docs/guides/database/views)。迁移时验证实际项目版本与权限，不能仅在管理角色下测试。

## 6. 图片后台推进：先处理正确性，再加调度

### 6.1 修复提交窗口与重复提交风险

阶段 1 调查时，创建任务和预扣积分已经在事务内，但上游网络提交在事务外，供应商任务编号在返回后才写入。直接让后台扫描无编号的 `pending` 项，会与原提交请求争抢；上游已接收、响应未落盘时还可能重复生成。阶段 2 已实现下列协议，具体参数和验收状态见[阶段 2 说明](task-center-stage-two.md)。

必须先完成以下改造：

1. 在创建任务的事务内一并领取原请求的提交租约；调用上游前持久化单项提交意图与尝试标识。明确区分未发送、发送中、已接收、提交结果待确认，关闭任务创建到首次发送之间的争抢窗口。
2. 原请求、页面推进与后台工作器使用同一领取协议。提交租约有效时，其他执行者只能读取状态。
3. 只有确认未发送，或供应商明确返回可安全重试的拒绝结果时，才允许原任务内补提交。继续沿用既有供应商限流退避策略。
4. 网络断开、进程硬停、响应丢失不能推导为“上游未收到”。有供应商幂等键或按请求查询能力时优先对账；缺少此能力时进入待确认，按原截止与退款规则收口，不盲目重新生成。
5. 老的进行中记录如果没有提交意图，且无法证明未发送，应保守处理；已经保存供应商任务编号的项可正常继续查询。
6. 用户手动重新生成必须使用新请求编号，并重新展示积分确认。任务中心不会自动重试整个失败任务。

此改造可以避免重复提交和重复结算，但不能保证每个供应商在响应完全丢失时都能找回已生成图片。无幂等或对账能力的上游仍可能产生平台成本损失，需要在验收与运营记录中明确。

### 6.2 复用推进器与租约

新增 `server/image-jobs/maintenance.ts`，提取并复用现有图片查询、下载、状态合并与 `BillingPort reserve/settle/release`。视频继续使用原维护器，不重复领取 `text_to_video`。

- 以 `next_poll_at`、截止时间和原有迟到结果规则筛选到期图片任务，按用户、供应商公平领取有限批次。
- 数据库短事务领取；网络查询与下载在事务外；最终写回重新校验领取令牌和有效租约。
- 用原任务行锁及领取令牌拒绝过期执行者写回，包含单项结果、任务终态与账本结算；不能只在领取时检查一次租约。
- 阶段 1 的图片租约为 30 秒；阶段 2 改为数据库时钟计算的 120 秒令牌租约，总 I/O 预算与单次请求/对象超时共同限制执行。过期重领与旧写回拒绝已通过本地双连接验收；视频维护器保持原协议。
- 批次领取使用锁跳过已领取行，避免并发阻塞；锁的是原任务行，不是聚合列表。[PostgreSQL 行锁语义](https://www.postgresql.org/docs/current/sql-select.html)
- 页面与后台统一遵守供应商并发/RPM限制、`next_poll_at` 与退避，不因页面数或浏览器标签数增加上游调用速度。
- 部分成功按原成功数量结算；重复执行不重复退分/扣分；迟到结果沿用已有不再收费规则，不重新定义计费。
- 结果转存成功并保存稳定对象标识后，才进入可展示的完成状态。转存重试复用原结果，不重新生成。

### 6.3 调度与请求时限

在原提交完成后可触发一次短后台推进；另外复用视频已有的 Supabase `pg_cron + pg_net + Vault` 模式，为图片建立独立分钟维护接口与调度。

新增内部接口：`POST /api/internal/image-jobs-maintenance`。使用独立密钥、恒定时间比较及当前运行环境校验；生产与预览密钥、任务范围、调度分开。不要复制视频密钥，也不要将 Vault 值打印到配置或日志。

每次调用有固定并发、批次上限与时间预算，初始预算建议 90 秒，留出当前 Vercel 120 秒函数时限的余量。不能领取超过本次可处理能力的任务，也不能通过长循环等待一个任务最终完成。

`waitUntil` 可让响应返回后继续执行，但仍受函数时限约束，不能代替下一次独立调度。[Vercel 函数包文档](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package)；Supabase 调度配置参考[官方定时调用文档](https://supabase.com/docs/guides/functions/schedule-functions)。

维护器同时补充按环境处理到期同步积分预留；邮件保留已有分钟维护。原每日图片清理保留兜底，并审计与新维护器同时执行时的锁和结算幂等。

分钟调度保证的是周期推进。关闭页面后，目标是在上游完成后的下一至两次正常维护周期内完成收取与状态更新；大文件转存耗时单独测量，不能宣传固定秒级完成。

## 7. 前端统一运行层

新增 `TaskCenterRuntime`，挂载在账号已就绪的应用根布局范围内，生命周期独立于侧栏展开、工具切换和任务抽屉开关。

### 7.1 查询与通知

- 摘要轮询初始策略：有进行中任务约 8 秒一次，空闲约 30 秒一次；提交成功、窗口重新聚焦时刷新。最终频率按请求量和实测调整。
- 隐藏标签页降低频率或暂停；服务端负责持续推进。网络失败指数退避，显示状态暂不可获取，不改写原任务终态。
- 统一 TanStack Query 查询键和任务订阅，协调现有 `useTaskPolling`，避免抽屉与工具页各自查询、重复弹通知。
- 原带推进行为的查询可在迁移期间兼容，但必须先纳入同一租约保护；任务中心摘要与详情始终保持只读。
- 账号/环境切换时取消未完成读取、清理内存与旧查询；迟到响应必须核对原账号身份后才能应用。
- 只在用户查看结果或既有业务恢复需要时调用素材持久化；不把所有历史结果自动下载到本地。

### 7.2 尚未取得任务编号

画布沿用 `GenerationRecovery`。其他新提交增加最小本地提交凭据：原请求编号、来源类型、工具/来源、时间及账号环境，提交前写入；不额外保存原图、蒙版或邮件正文。

刷新后先用原请求编号查询服务端，与列表按请求编号合并；已找到则继续读取原任务。未找到时显示待确认，不能因一次 404 或网络错误自动创建收费请求。工具缺少原输入时提示重新准备输入，画布仍走已有继续/放弃流程。

本地凭据只是寻找原请求的线索，不是新的执行队列，也不代替服务端事实。画布“放弃”继续只停止本地恢复，不能显示成取消上游或已经退款。

非画布的本地待确认凭据有数量与保留时间上限；找到对应服务端任务后移除。画布恢复记录继续遵守原项目持久化规则，不能被全局凭据清理误删。

### 7.3 稳定结果身份

复用现有 `resultIdentity`、工作站历史和资产登记路径，以任务编号、结果序号、对象键关联结果。签名地址刷新不能制造新素材；多次查看同一任务、刷新恢复、部分成功补图都只登记对应结果一次。

## 8. 各工具定位与恢复

统一内部任务查询参数建议为 `task=<sourceKind>:<sourceId>`，服务器重新校验归属；路由只是定位线索，不能用它跳过权限检查。

| 入口 | 导航与恢复行为 | 草稿保护与降级 |
| --- | --- | --- |
| 工作站图片任务 | `/image-workstation/:tool?task=...`；绑定已有任务，恢复等待与输出预览 | 当前输入/蒙版不被覆盖；来源参数能完整恢复时提供显式载入 |
| 同步消除/重绘/扩图 | 对应工作站页面的已有任务模式，按原同步记录显示结果 | 缺少原蒙版与原图时只读查看；显式把输出作为新输入 |
| 抠图 | `/toolbox/bg-remove?task=...`，显示原任务结果，复用抠图历史 | 不重跑上传；与已保存本地队列按结果身份去重 |
| 转比例智能扩展 | `/toolbox/aspect-ratio?task=...`，查看已提交单项结果 | 不自动重建未保存的整批队列或重复执行剩余项 |
| 自由画布 | 原 `/canvas/:mode` 携带 `projectId`、`projectSource` 和任务标识；进入原场景，复用占位图恢复 | 通过现有 `ProjectOpenGate`；原项目不在本机/不可访问时展示任务结果，不自动建项目或覆盖当前画布 |
| 视频 | `/canvas/text-to-video?task=...` 携带可用的原项目来源，复用 `VideoPlayer`、视频资产登记 | 同样通过画布项目门禁；功能未开放时可查看有权限的历史结果，不借此开放生成能力 |
| 邮件 | `/email?task=...`，查看对应已提交项和文本结果 | 不覆盖未保存文本、不重新导入 CSV、不自动提交剩余批处理 |
| 来源缺失的旧任务 | 统一只读详情；可确定工具时提供显式打开 | 不猜测画布项目、场景与原本地输入 |

画布路由目前打开项目后会移除查询参数；改造时必须保留经过校验的任务标识，再执行场景定位。不能绕过未完成生成、保存失败、云端冲突和编辑权等已有项目切换限制。

任务解析需要响应同一页面内的查询参数变化，不能只在组件首次挂载时执行。查看和恢复路径不得调用 `createTask`、同步生成 POST 或批处理启动函数。

| 侧栏与无障碍 | 68/168/260 像素宽度、短视口、375/768 像素页面宽度可用；键盘可达，文字/图标配色 | 浏览器测试 |
| 维护分发失败/函数超时 | 失败可见且下一轮可继续；202、cron 成功不能单独算业务成功 | 调度 + 故障注入 |

测试优先复用现有 Vitest、数据库测试基础和浏览器模拟供应商，不为纯样式改动堆叠实现镜像测试。实现阶段执行相关测试、必要回归、`build`、`lint`、`git diff --check`，并检查 Vitest 的 `Unhandled Errors`，不能只看断言数量。

真实供应商验收至少覆盖一条异步图片任务和一条同步工具任务，用测试账号和最小合理规格记录实际消耗。模型之间的提交与结果行为不同，应按实际启用的供应商类别验证。视频未开放或无测试条件时明确记为待验收，不能用空队列维护日志代替生成成功证据。

## 12. 迁移、灰度与回滚

### 12.1 发布顺序

1. 在实施时通过 Supabase CLI 生成迁移文件；先做可空列、可兼容表/索引与领取函数，不提前杜撰迁移时间戳。
2. 本地和预览验证实际应用角色、RLS、索引计划、旧提交协议及旧查询协议。
3. 发布服务端提交保护和维护器，先启用预览范围图片调度，完成关闭浏览器和并发故障验收。
4. 在获准的上线窗口执行生产迁移，发布兼容服务端；确认视频与邮件既有维护不受影响。
5. 独立启用生产图片分钟调度，核对从调度分发到任务与账本完成的整条证据。2026-10-12 已创建 `aigc-image-maintenance-production`（`* * * * *`，请求体 `{"scope":"production"}`），并完成一笔生产关页收取、转存和结算，详见[阶段 2 说明](task-center-stage-two.md#6-生产分钟维护2026-10-12)。上游账单核对仍待做。
6. 再灰度启用任务中心 API 与前端；新来源字段必须在服务端接受之后再由客户端发送。
7. 验收工作站、画布、同步工具的真实刷新恢复后扩大使用范围。

不回填无法证明的原画布来源；历史工具信息可以按明确规则推导。迁移只作用于 AIGC 所需对象，不能扩大到共享 Auth 或其他产品的任务/账本。

### 12.2 开关与回滚

- 任务中心 UI 开关与图片后台开关分开，隐藏 UI 不应停止已接收任务的收取与积分收口。
- 新生成能力关闭时，已有供应商任务仍可查询与收尾。
- 前端/API 故障先回滚展示层；兼容服务端、后台与新增可空字段保留，不删除账本和任务结果。
- 若工作器出现重复提交风险，立即停止危险提交分支；保留按已有供应商编号查询、结果转存、超时退款和每日兜底。
- 回滚版本需要兼容已经创建的提交意图和领取记录，不能回到会盲目补提交的旧推进逻辑。
- 2026-10-12 已启用的生产图片分钟维护，回滚顺序见[阶段 2 说明](task-center-stage-two.md#62-回滚)：先 `cron.unschedule('aigc-image-maintenance-production')`，再把生产 `IMAGE_MAINTENANCE_ENABLED` 设为 `false` 并重新部署。

## 13. 运行观测与上线门槛

日志最小字段：任务类型/编号、运行环境、供应商、领取尝试、维护耗时、成功/失败/待确认数量、转存结果和账本收口结果。不记录提示词、邮件正文、原图、密钥、签名 URL。

重点观察：到期任务积压、最老未收口预留、提交待确认数量、租约过期/旧写回拒绝、上游限流、转存失败、维护连续失败。利用现有日志与项目数据库，不增加第三方分析服务。

上线门槛：

- [ ] 两个账号、`local/preview/production` 的任务与展示状态隔离通过实际应用角色验证。
- [ ] 无浏览器在线的图片任务，后台能独立保存结果并完成账本收口。
- [ ] 刷新、恢复、点击查看、并发领取没有产生额外上游生成请求或第二次结算。
- [ ] 同步结果过期、提交待确认、部分成功、退款等待等状态能准确区分。
- [ ] 工作站草稿、画布项目切换保护、现有视频/邮件后台与资产身份无回归。
- [ ] 生产调度证据包含 cron 状态、网络分发、服务端完成日志、任务终态、存储结果与积分记录；真实供应商还需核对上游账单。2026-10-12 已有一笔 Qwen Image 3.0 的生产分钟收取、R2 转存和 3 积分结算，结果 1328×1328，无退款、无重复提交。上游账单仍未核对，本项不勾选。
- [ ] 真实测试与模拟测试分别记录；未测模型、暂未开放视频等限制写入验收报告。
- [ ] 页面窄屏、短视口、键盘操作与侧栏缩放可用。
