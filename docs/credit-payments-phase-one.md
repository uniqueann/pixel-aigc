# 首期积分商业化

本期为个人钱包增加按需充值、同步图片扣分和现金退款审核。订阅、团队共享和正式视频收费留在后续阶段。既有视频开关保持原设置。

- 消除、重绘每次 5 分；扩图实际一轮 5 分、两轮 10 分。无法提前确认轮次时提示最多预扣 10 分，一轮成功退回多预扣的 5 分。

- 主体检测、智能选区保留限流，不单独收费。裁剪、普通转比例、加水印、布局和本地保存免费。邮件助手继续 BYOK 和现有限流。
- 新钱包仅首次赠送 30 分；已有钱包及历史流水不变。购买积分不设到期日。积分不能提现，赠送积分不折现。

## 订单与积分事务

独立 `aigc.credit_orders` 保存用户、环境、支付模式、商品、币种、金额和积分快照。支付 metadata 使用 `productScope=aigc`，不用 EDM 商品和 workspace。EDM 仅作为接入方式的参考，未修改 EDM。

创建支付链接前，服务器查询商品并校验价格和类型。`/api/payments/creem/webhook` 与 `/api/payments/dodo/webhook` 在身份认证前处理，先验证原始请求体签名，再重新查询平台付款记录并核对 metadata、商品、金额、币种和支付状态。前端返回参数只触发查询，不能发积分。

到账事务锁定订单，更新订单状态、余额和 `order:<订单UUID>` 充值流水；付款编号在通道及模式内唯一。用户角色 `aigc_api` 无到账权限，后台角色 `aigc_billing_worker` 无直接余额写权限。定时补偿和用户查询共用到账事务。配置禁用充值只阻止新购买，已有订单仍可处理回调和对账。

`/api/internal/credit-payments-reconcile` 使用 `CRON_SECRET`，处理有支付链接的近期未到账订单。已加入每日调度；页面返回时每 5 秒查询，最多 12 次，仍可手动查询。上线时按实际订单量增加受保护调度频率。一次补偿限制运行时间，超时或供应商故障保留待查询状态。

## 收费图片与恢复

客户端提交随机 `billing.requestId`、`priceVersion`、已确认的 `maxCredits`。服务端保存内容指纹，按请求编号锁定和预扣，成功保存私有图片再结算，失败退款。重复提交同一请求只返回已存结果或处理中状态，不重复调用供应商。请求编号与内容冲突时拒绝。

所有收费同步结果都写入既有 `temporary/<工具>-results/<用户>/...`，复用私有读取与 7 天临时对象生命周期。余额与计费记录永久保留，临时结果不永久保留。网络中断仅查询已有操作；仍在处理的操作可在积分明细中查询。超时收口由下一次积分查询或每日清理执行；硬超时最长等待到下一次调度，不承诺立即退款。大图传输、失败图片的主动重试和现有对象读取保留。

## 人工现金退款

用户在充值订单中提交原因。现金不自动退还，后台只自动处理生成失败的积分退款。

1. 使用 `npm run aigc:payments -- refunds production` 查看审核申请。
2. 查订单、流水、实际支付账单及未使用积分，先确认平台没有正在进行或已完成但尚未回调的退款。未使用积分按赠送和旧余额优先消耗核算；后续充值不能恢复旧订单的退款额度。管理员手动调账可能使可退额度保守缩小，应结合流水审核。
3. `AIGC_ADMIN_OPERATOR` 必填。在本地管理员环境执行：`npm run aigc:payments -- prepare-refund production <订单UUID> <累计退款美分或人民币分> <审核幂等键> <审核原因>`。数据库只冻结可退积分，现金尚未退还；全额/部分金额按累计金额比例向上取整收回整数积分。
4. 人工在原支付平台对同一付款原路退款。回调按累计退款金额确认收回，已冻结的积分不重复扣减。平台额外退款或争议导致余额不足时余额保持非负并冻结后续收费，记录欠收积分，交人工核对。
5. 若退款操作未执行或明确失败，先在平台确认没有已完成及进行中的现金退款，再执行 `npm run aigc:payments -- cancel-refund production <审核幂等键> --verified-no-cash-refund <核验原因>` 释放积分。现金记录已变化时数据库拒绝释放。不要把未收到回调当作退款失败。

Creem 退款事件使用验签后的累计金额；Dodo 重新查询付款的已成功退款汇总。乱序退款不会减少已记录的累计金额。争议及退款先于到账的异常订单进入人工核对，不能重新自动发放整包积分。

## 部署前准备与验收

使用现有迁移流程应用 `20261004152128_aigc_credit_payments.sql`，再部署对应前后端，避免旧客户端缺少收费报价字段。迁移为现有 `aigc_server` 授予独立后台角色；新 bootstrap 同样授予该角色。不将管理员连接部署到 API。

按 `.env.example` 配置独立的 AIGC 三档 TEST/LIVE 商品、密钥、回调签名密钥和固定站点 origin。local/preview 只读 TEST，production 只读 LIVE。收款主体参考 EDM 的商户账号，但要单独配置 AIGC 商品及回调，验证其有权销售本产品。不要复制 EDM 的订阅商品 ID。

当前实现默认 `AIGC_PAYMENTS_ENABLED=false`。开启真实收款前必须完成：

- 商户账号、支付方式、最终币种、含税售价、商品类型及真实净到账手续费核对。
- 两个独立登录账号各做充值与图片操作，确认生产用户、运行环境及 EDM 隔离。
- TEST 的真实平台签名回调、重放、丢失后的补偿查询、部分现金退款及审核取消。
- LIVE 一笔明确授权的小额支付与到账、一笔明确授权的原路退款、真实供应商失败退款及实际轮次扣分。
- 根据真实供应商与支付账单核算毛利，视频成本确认前保持关闭。

本地 PGlite 测试是真实 SQL 事务与 RLS 执行，但不是远程 Supabase 或多连接压力测试；供应商和支付 API 单元测试使用受控响应，不能替代真实平台验收。
