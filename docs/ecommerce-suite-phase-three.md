# 电商套图阶段三：持久编排与任务聚合

基线：`main / fb046e7`，PR #195 已合并。开发分支：`feat/ecommerce-suite-phase-three`。

本阶段把已确认的生成计划交给服务端持久队列，接入整套报价、限并发派发、停止和手动重试，以及任务中心父批次。验证使用本机独立 PostgreSQL、模拟供应商、内存对象存储和浏览器合成 HTTP 数据；真实目标环境调度、R2、供应商与九个商品样本尚未验收。

## 1. 计划与费用确认

工作台提供“整套计划／风格重生成”，选择启用槽位、图片模型和分辨率，每个生成槽位默认一张候选。单槽位入口仍可选择模型支持的候选数量。统一风格先在商品资料中编辑并保存，重生成保留旧版本。

报价逐项展示处理方式、服务端合成要求、实际规范化规格、候选数量、单价及合计。主图复用主体照片，细节必须有真实输入；尺寸图只允许复用用户上传并确认标注的尺寸成品，同时要求已确认尺寸或容量事实。缺少输入时不能报价相应槽位，不能把无标注原图记为已完成尺寸图。自动标注仍属第四阶段。

接受批次时锁定项目和报价，核对十分钟有效期、修订、指纹、实际映射及预算，只保存批次与操作，不预扣、不访问供应商。操作在此获得稳定原请求号及不可修改的计划列；同请求返回原批次，同报价只能接受一次，同项目最多一个活动批次。已接受报价过期不影响其三十分钟派发窗口。

派发时重新核对目录与冻结参数；模型、价格、渠道或输出规格变化需要重新确认。原任务创建、原 `BillingPort.reserve`、items 和操作绑定共享一个 SQL 事务；供应商 I/O 在事务之外。父批次没有独立账本、预扣或退款状态机。

## 2. 领取、恢复与收口

迁移：[20261017052816_ecommerce_suite_phase_three.sql](../supabase/migrations/20261017052816_ecommerce_suite_phase_three.sql)。新增冻结计划、令牌、租约、下次尝试时间和运行编号；迁移兼容已接受的阶段二单槽位记录。

`aigc.claim_due_suite_operation` 是唯一跨账号领取入口：只接受与事务环境相同的 scope、空维护账号和运行编号，固定空 `search_path`，撤销公共与 Data API 角色执行权限。采用项目 → 批次 → 操作的加锁顺序及 `SKIP LOCKED`；当前环境最多四份有效租约，每账号套图派发并发为一。原图片服务的用户／小时／模型／供应商及全局限制继续生效。[PostgreSQL 行锁语义](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)

维护器每轮最多七项、预算 85 秒，租约 120 秒，网络和图片处理均不占持锁事务。结果对象读取有 20 MiB 限制并使用本轮中止信号。处理器记录运行编号、环境、领取、派发、登记、过期令牌拒绝与错误；日志不包含商品提示词、签名 URL 或密钥。

- 先检查原绑定与稳定请求号，包括已过期原任务；原凭据存在就只观察、补绑定或登记，不能重新创建。
- 新创建后复用原 `advanceImageClaim`。后续供应商确认、轮询、超时与结算仍由原图片维护器负责，套图不会实现第二份供应商执行器。
- 已知未创建的容量／频率限制按原 `retryAfterSeconds` 推迟首次派发。余额不足、计划变化或输入缺失阻塞全部尚未执行项。
- 三十分钟到期、主动停止或删除项目，停止尚未绑定的项并使旧令牌失效；已绑定任务继续执行和结算。全局首发或原图片维护关闭时不新建任务，已有结果仍可登记，截止与停止仍生效。
- 原创建事务响应不明时保留稳定请求号；下一轮先找原任务。领取令牌在绑定和转存后的最终写入时再次核对，过期执行者不能应用结果。
- 结果登记按原 job＋ordinal 幂等追加版本。对象转存或落库失败仅修复保存，不重新生成或计费。后台无法判断本机是否有未同步草稿，因此**所有结果先保存候选，当前版本由用户显式选择**。
- 批次完成以原任务终态和结果登记为准；等待候选选用不占活动名额。项目保留旧成品，部分失败不会清空成功槽位。

## 3. 停止与手动重试

批次面板展示每个槽位的等待／派发／确认／阻塞／停止状态、候选、原任务费用及可处理原因。停止只作用于未创建原任务的操作，不保证取消已接收的上游任务。

重试必须勾选未执行或明确失败且没有成功候选的槽位，重新获取报价并确认。服务端验证原批次已经没有待收口或 confirming 原任务，接受时在同一事务终结旧未派发项，令旧令牌失效，再创建带 `retryOfOperationId` 的新批次。每个旧操作只能关联一次后续尝试；旧失败已有后续结果时必须转到最新批次，不能绕过新结果重复重试。不能通过重试入口重复成功槽位；整体风格重生成则是用户明确选择的独立新计划。

本机未知提交仍保留原批次请求编号，恢复只 GET 找回；活动页面仅 GET 更新读模型，不负责派发或推进原图片任务。明确的“派发未启用”拒绝可以清除本机待确认标记，网络事实不明时不能清除。

## 4. 任务中心与定位

新增只读 `suite_batch` 身份，原图片任务仍为 `image_job`，费用只聚合原账本。列表和侧栏折叠属于同批次的图片项，活动计数不重复累加父子；原任务详情和按原请求恢复保持可独立访问。

父批次使用目标槽位作分母；子任务继续用候选张数作分母。七槽位中两项失败、某槽位四候选两成功时，父级可为 5/7，子级为 2/4，不能相互替换。原任务清理后仍保留操作凭据，费用从原账本查找；缺少账本显示结算未知及已知金额，未创建原任务显示未预扣。

父批次详情列出原图片任务，支持进入原详情和返回 `/ecommerce/:id?batch=:batchId`；子任务保留槽位定位。独立批次只读接口可定位超出项目最近三十批次范围的旧批次，不猜测其他项目。扩展游标校验、已读／隐藏归属策略和清理规则；功能开关关闭时沿用不读取套图表的原任务投影。

## 5. 目标环境启用与回退

入口和维护默认关闭。本次未修改远端数据库、对象桶、调度或部署配置。

1. 通过正常迁移流程应用阶段二、三迁移，检查实际 `aigc_api` 权限、旧单槽位兼容和任务中心原功能。
2. 先确认原图片分钟维护健康；保留现有 `IMAGE_CRON_SECRET`、`IMAGE_MAINTENANCE_ENABLED` 和 `IMAGE_BACKGROUND_SUBMIT_ENABLED` 保护。生产、预览密钥和调度分开。
3. 按现有 Supabase Cron＋Vault＋`net.http_post` 部署方式，新增每分钟 POST `/api/internal/ecommerce-suite-maintenance`，请求体只传当前环境，例如 `{"scope":"production"}`。复用独立图片维护密钥；不要把密钥写进迁移、前端、文档或日志。内部入口返回 202 与 runId，执行通过 `waitUntil` 纳入函数生命周期。
4. 验证迁移后先受控设置 `ECOMMERCE_SUITE_ENABLED=true`、`ECOMMERCE_SUITE_MAINTENANCE_ENABLED=true`。仅四个功能／维护／首发开关全部满足时接受新计划。
5. 使用已确认费用上限的真实商品批次，关掉浏览器，至少连续两轮核对调度、套图运行日志、原任务和账本，直到尚未提交项独立派发、结果落库并完成。返回 202 或前端轮询不能代替此验收。
6. 回退时先取消套图定时任务，再关闭套图维护和入口开关并部署；原图片维护继续收口已提交任务。保留表、版本、资产与账本，未执行项到期停止。

## 6. 验证范围

本地证据见[阶段三验收记录](verification/ecommerce-suite/phase-three/README.md)，执行 `npm run test:ecommerce-suite:postgres` 必须提供明确确认的本机空白独立库。该脚本会运行完整迁移链、实际应用角色和原 SQL 账本，供应商及对象存储为模拟实现；拒绝业务库和非本机地址。

连续维护测试实际调用原图片维护器和套图维护器；为缩短本机验收，脚本主动把下次尝试／轮询时间置为到期，不代表真实分钟调度。原图片维护器新增可选对象清理端口以使用测试对象存储，生产默认行为不变。

覆盖七槽位计划与并发接受、领取和停止、租约过期与晚到、无浏览器维护轮次、最后积分争用、限流／目录变化／余额／截止、部分候选结算、父子计数、原请求只读恢复、转存失败及过期令牌写回拒绝。

尚未完成目标环境关页持续派发、真实供应商与 R2、九个真实商品样本，因此阶段三发布退出条件仍未通过。图层编辑、工作站回填、恢复包导入、平台预检和批量成品导出仍在后续阶段。
