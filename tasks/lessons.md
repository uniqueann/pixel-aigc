# 经验记录

## 上传排查先确认实际 Origin，域名变更同步存储 CORS

- 触发：按旧正式域名 aigc.contentup.cc 测试上传成功，但用户实际访问的是 aigc.pixelsai.app；后者未加入桶 CORS，预检持续返回 403。
- 规则：先确认用户实际页面的 Origin，再用该来源执行 OPTIONS 与浏览器上传验收；域名绑定或迁移时同步核对 R2 的精确来源列表。旧域名、固定域名或预览地址成功，不能证明其他来源可用。
- 验证：本次仅新增 https://aigc.pixelsai.app，预检从 403 变为 204，真实 4 MiB PUT 返回 200；费用接口保持阻断。缺少跨域头的存储错误也会表现为 Failed to fetch，不能仅按前端异常名称归因。

## 合法大图上传失败不能归因于业务超限

- 触发：上传预检改动后，用户反馈 4 MB 扩图仍失败，文案误导为图片太大。
- 规则：分别验证业务上限、编码后的传输预算和首次失败阶段。直传异常后的回退受限，必须保留直传失败原因；只拦住必然失败的回退不能宣称已恢复合法大图上传。
- 验证：请求预算必须同时覆盖平台与服务端限制；mock 上传成功无法证明浏览器 CORS 与真实直传正常。没有实际响应、配置或日志时，不把 CORS、网络或平台错误来源写成已确认根因。

## 吸顶元素改变高度时要关闭滚动锚定

- 触发：移动端工作站吸顶卡切换紧凑态后，卡内图片在贴顶临界点反复抖动。
- 规则：只要 sticky 元素在滚动中会改变自身高度（展开/压缩/内容增减），就检查所在滚动容器的 `overflow-anchor`；Chromium 的滚动锚定会反向修正 `scrollTop`，与「是否贴顶」的判定形成反馈循环。
- 原因：锚定想保持内容视觉位置，贴顶判定却依赖 `scrollTop` 与元素顶边；两者互相调整时状态机不会收敛。优先在滚动容器上关闭锚定，而不是给判定加滞回或删过渡。

## 工具箱同类交互必须横向对齐

- 触发：用户发现智能抠图与加水印在页签切换记录、移动端预览吸顶、完成态底栏三处行为不一致。
- 规则：改动任一工具箱的会话、布局或底栏时，先对照相邻工具；能共享的逻辑抽到 `shared/`，并用同一组 Playwright 场景同时验证两页。
- 原因：两个页面共用 `toolbox-watermark` 样式与相近结构，但状态管理各自实现，容易出现只修一边、另一边继续漂移。

## 加高移动端卡片时要检查吸底操作栏遮挡

- 触发：融合移动端改为自适应高度后，第二个槽位的「替换」按钮被 98px 吸底操作栏盖住，`elementFromPoint` 命中页脚而不是按钮。
- 规则：移动端卡片高度变化后，除检查内部 `overflow` 裁切，还要用 `elementFromPoint` 测底部主操作的命中元素；必要时压低媒体高度，或给滚动容器预留页脚高度。
- 原因：吸底操作栏是 sticky 覆盖层，不占文档流；内容变高后底部控件会滑到它下面，只看截图容易漏掉。

## 同屏对比的两层必须共用同一显示框

- 触发：精修画布做前后对比时，原图 480×480、结果 1024×1024；fit 模式下若用 `max-width/max-height` 让两张图各自决定显示尺寸，原图只占中间一小块，分割线两侧对不齐。
- 规则：对比层统一 `width:100%; height:100%; object-fit: contain`，1:1 时再改 `object-fit: fill`；不要依赖 `max-width/max-height` 保留自然尺寸。
- 原因：分割线是按同一框宽度的百分比定位的，只有两层共享同一几何，裁剪位置和标签才一致；小图放大带来的轻微模糊是可接受的代价。

## 输出尺寸承诺要三处同时保证

- 触发：做精修「保持原尺寸」时，只改客户端 `size` 并不会改变模型输出像素，服务端 `cropToSourceAspect` 原先只裁比例不缩放，客户端又只校验「声明尺寸 vs 实测尺寸」。
- 规则：任何「输出就是 N×N」的承诺，都要在客户端推导目标尺寸、服务端后处理真正 resize、并把 resize 后的宽高写回 descriptor / result_width / result_height 三处对齐；只改其中一处会导致界面承诺与实际文件不符。
- 原因：计费按档位、生成按档位、交付按原像素，三者是不同层；档位推导集中在 `shared/retouch.ts` 才能让报价、请求、文案永远一致。

## 同步接口的「生成中」要靠 submitting 而不是 active

- 触发：给消除/重绘制画布加生成浮层时，页面原本的 `processingLabel` 用 `controller.active || controller.submitting`，而这类任务走同步 `Capability.Inpaint`，返回即是 `succeeded`，`active` 恒为 false；同时 mask-paint 分支根本就没渲染这个 prop。
- 规则：判断同步任务是否在跑，用 `submitting`（覆盖读原图→导出蒙版→上传→往返）叠加 `readingResults`（下载解码）；两者都真时读取阶段优先。给状态浮层加闸门时别漏掉 `retryRead`：它只置 `readingResults`，`submitting` 仍为 false。
- 原因：`active` 来自任务状态集合，只对异步任务有意义；把两种链路的 busy 语义混在一个表达式里，必然在同步链路上静默失真。

## 复用状态浮层类之前先查它在媒体查询里被怎么处理

- 触发：消除/重绘的阶段浮层本想直接复用 `.workstation-canvas-state`，但移动端 `.is-stuck .workstation-canvas-state { display:none }` 会在用户滚到设置区等结果时把提示藏掉。
- 规则：新浮层要么用独立类并在媒体查询里显式声明保留，要么先确认旧类的所有 `display`/`visibility` 覆盖；不要靠「DOM 顺序碰巧赢」推断它会显示。
- 原因：这类「吸顶紧凑态隐藏次要元素」的规则是为静态信息写的，对「正在生成」这类必须可见的反馈是错的；用计算样式实测比读 CSS 更可靠。

## 重试失败状态不要用 effect 重置

- 触发：在 effect 中根据 `resultReadError` 清空 `retryReadFailedAgain`，既触发 `react-hooks/set-state-in-effect`，又会在重试读取阶段把刚设置的「仍无法读取」提前抹掉。
- 规则：把「是否重试失败」按任务 id 派生（`retryReadFailedTaskId === activeTask?.id`），不要在 effect 里同步 setState。
- 原因：effect 在错误清空的瞬间也会运行，无法区分「换任务」和「正在重试」；派生状态会随任务 id 自动失效，换图或新任务不需要额外清理。
